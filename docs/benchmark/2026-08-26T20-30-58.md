## 歸因

基準線（`direct`）是**不經過網關**直接打上游，它包含了壓測端與假 Provider 自身的延遲。
網關造成的額外延遲要用各組減去它才有意義。

每一組的**量測解析度**是該組觀察到的壓測端抖動：小於它的差距不能宣稱測得出來。

- `virtual`：p95 1215ms − 基準線 888ms = **+327ms**（解析度 ±64ms）
  → 差距大於解析度，是可以宣稱的結果。
- `platform`：p95 4062ms − 基準線 888ms = **+3174ms**（解析度 ±144ms）
  → 差距大於解析度，是可以宣稱的結果。

## 這份報告的有效性條件

- 三組在**同一次執行、同一台機器**上取得，暖機條件相同。
- 每一條串流都經過驗證（HTTP 200、確實收到 token、以 `[DONE]` 收尾）；
  只要有一項不成立就計為失敗，不會被算進 TTFT 分位數。
- 量測端抖動超過該輪 TTFT 25% 的輪次標記為無效——
  抖動與訊號同數量級時，量到的主要是壓測端自己的排隊延遲。
- 抖動本身即為**量測解析度**：小於它的差距不做宣稱。
- 每一輪前後都確認上游假 Provider 仍然存活。
- 分位數取各輪的**中位數**並附上區間，不是把所有樣本混在一起。
- 堆積用量取自 JVM 自己的 `jvm_memory_used_bytes{area="heap"}`，而非作業系統的常駐頁數——後者會被 Windows 主動修剪，量到的是殘值。
