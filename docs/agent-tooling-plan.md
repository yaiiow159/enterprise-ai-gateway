# Skills 與 Hooks 規劃

判斷標準：**會重複做、且做法有非顯而易見的細節**的事才值得包成 skill；
**每次改動都該立刻檢查、且成本在數秒內**的才適合做成 hook。
一次性的事直接做就好，包成 skill 只是多一層維護。

這個專案有一個和一般後端專案不同的前提：**被測系統的下游要花錢、會抖動、
而且不能在 CI 裡呼叫**。工具鏈的優先序完全被這件事決定。

---

## 建議優先序

| 優先 | 名稱 | 型態 | 什麼時候做 | 為什麼值得 |
| --- | --- | --- | --- | --- |
| 1 | `fake-provider` | 服務 + skill | ✅ 已實作 | 沒有它，路由、對沖、串流、失敗切換全都無法驗證 |
| 2 | `dev-stack` | skill | ✅ 已實作 | Redis／PostgreSQL／Qdrant／假 Provider 一鍵起，並等到真的可用 |
| 3 | `stream-check` | skill | ✅ 已實作 | 串流的錯法都很隱蔽：緩衝、斷線不取消、token 遺漏 |
| 4 | `cost-guard` | skill + hook | ✅ 已實作 | 這個專案唯一會「一個 bug 燒掉真金白銀」的風險 |
| 5 | `bench` | skill | ✅ 已實作 | TTFT 與 tokens/s 是這類系統的核心指標，與一般 QPS 不同 |
| 6 | `rag-eval` | skill | ✅ 已實作 | 嵌入不一致是靜默失效：檢索照常回結果，只是全都不相關 |
| 7 | `release-check` | skill | 最後 | 把上述串成一次交付把關 |

## 1. `fake-provider` ✅ 已實作

**做什麼**：一個可控的假 LLM 服務，實作 OpenAI 相容的 `/v1/chat/completions`，
包含 SSE 串流。行為完全由請求參數或設定控制：

- 首個 token 延遲（TTFT）與每 token 間隔
- 指定的錯誤碼與錯誤內容（429、500、逾時、連線中斷）
- 串流到一半中斷
- 回報的 token 用量與模擬價格

**為什麼是第一優先**：這個專案的所有核心功能——依延遲路由、對沖取最快、
Provider 失敗切換、熔斷、串流轉發——都**只有在下游行為可控時才驗證得了**。
用真的 Provider 測，等於每跑一次測試就付一次錢，而且延遲每次都不同，
「取最快的那個」到底有沒有生效根本無從斷言。

**驗收**：能穩定重現「Provider A 固定慢 2 秒、Provider B 正常」，
且網關的對沖邏輯每次都選到 B。

## 2. `dev-stack` ✅ 已實作

**做什麼**：`docker compose up -d` 之後逐一等待 Redis／PostgreSQL／Qdrant／
假 Provider／Prometheus／Grafana 真的可用，並在啟動前檢查連接埠衝突、指出佔用者。

**為什麼**：容器 `Up` 不等於服務可用（PostgreSQL 初始化、Qdrant 載入 collection 都要時間）。
另外這台機器上已經有其他專案佔用 6379／9090／3002，
`docker compose` 的 bind 失敗訊息不會告訴你是誰佔的。

（FlowSentinel 專案已有同樣的腳本，可直接沿用結構。）

## 3. `stream-check` ✅ 已實作

**做什麼**：對 SSE 端點做端到端驗證，斷言的是**串流特有的錯法**：

| 檢查 | 為什麼會錯 |
| --- | --- |
| TTFT 在合理範圍 | 中間任何一層做了緩衝，首個 token 就會等到整段生成完才吐出來 |
| chunk 是逐段抵達而非一次到齊 | 同上，且用一般的 HTTP 測試工具看不出來 |
| 客戶端斷線後上游請求被取消 | 沒取消就是持續在燒錢，而且沒有任何錯誤徵兆 |
| token 不重複、不遺漏 | 轉發時的邊界處理錯誤，內容會少字或重複 |
| 錯誤事件格式正確 | 串流到一半失敗無法「收回」，客戶端要能分辨正常結束與中斷 |

**為什麼值得**：這些問題在瀏覽器裡手動點一次通常看不出來——
內容最後都會出現，只是慢，或者是花了錢卻沒人發現。

## 4. `cost-guard`（含 hook） ✅ 已實作

**做什麼**：兩層。

**靜態掃描**（適合做成 hook，秒級）：
- Provider 請求沒有設定 `max_tokens` 上限
- 重試沒有退避或沒有次數上限
- 對沖被設成無條件觸發（而非延遲對沖）
- 金鑰樣式（`sk-`、`anthropic-` 等）出現在原始碼或設定檔

**執行期預算檢查**（skill）：
以假 Provider 跑一輪典型流量，統計「若以真實價格計算會花多少錢」，
並比對設定的每日上限是否真的會攔截。

**為什麼值得**：這是本專案唯一會**直接造成金錢損失**的風險類別。
一般後端的 bug 是服務壞掉，這裡的 bug 是帳單。無條件對沖、失控重試、
沒有 `max_tokens` 的請求，任一個都足以在無人注意時燒掉大筆費用。

## 5. `bench` ✅ 已實作

**做什麼**：量測 TTFT（p50/p95/p99）、tokens/s、併發連線數下的穩定度，
以及平台執行緒與虛擬執行緒的對照。

**與一般 QPS 壓測的差別**：LLM 網關的每個請求都是長連線、長時間、低 CPU，
「每秒完成幾個請求」不是重點，**「同時能維持幾條串流」與「第一個字多久出現」**才是。
壓測工具必須支援 SSE 並個別記錄 TTFT。

（FlowSentinel 的 `bench` 已經處理過幾個坑可直接沿用：壓測端要多程序、
每組量測前後強制清掉殘留 JVM、請求要有逾時。）

## 6. `rag-eval` ✅ 已實作

**做什麼**：
- 啟動前檢查向量庫 collection 的維度與距離度量，和目前設定的嵌入模型是否相符
- 對一組固定的問答集量測 recall@k，作為換模型或改分塊策略時的迴歸基準

**為什麼值得**：嵌入不一致是**靜默失效**——用 A 模型建索引、用 B 模型查詢，
向量庫照樣回傳最近鄰，只是全部不相關。系統不會報錯，只會變笨。
維度不同會直接報錯（那算幸運），維度相同但模型不同才是災難。

## 7. `release-check`

把上述串成一次執行並產出報告：建置與測試、串流驗證、成本靜態掃描、
（`--full` 時）壓測與 RAG 評估。阻擋項目失敗以非 0 結束，可直接接進 CI。

## Hooks 建議

| Hook | 時機 | 動作 | 成本 |
| --- | --- | --- | --- |
| **金鑰外洩防護** ✅ | `PreToolUse` on Write/Edit | 內容含 Provider 金鑰樣式就**阻擋寫入** | 即時 |
| 成本風險掃描 ✅ | `PostToolUse` on Write/Edit of `.java`／`.yml` | 只在**阻擋級**發現時出聲，不阻擋 | < 1s |
| SSE 端點提醒 | `PostToolUse` 改到串流相關檔案 | 提示跑 `stream-check`（不阻擋）| 即時 |

金鑰防護是這個專案最該做的 hook，而且要用 `PreToolUse` **阻擋**而非事後警告——
金鑰一旦寫進檔案並提交，就算後續刪掉也已經留在 git 歷史裡，
正確的處理是輪替金鑰，成本遠高於當下擋下來。

**刻意不做的**：
- 「每次存檔就 `mvn compile`」——Maven 冷啟動數十秒，會把每個小修改變成等待。
- 「每次存檔就跑測試」——整合測試要起容器，更慢。
- 「自動呼叫真的 Provider 做煙霧測試」——每次存檔付一次錢，而且會因額度用盡而失敗。

先做 `fake-provider` 與 `dev-stack`。這兩個不依賴尚未存在的業務程式碼，
而且**第一天寫路由邏輯就會用到**——沒有可控的下游，路由與對沖根本無從驗證。

## 實作後補記（2026-08-26）

做 `fake-provider` 時，它的自我驗證（`smoke.js`）當場抓到兩個自己的缺陷。
兩個都屬於「不寫測試就永遠不會發現」的類別，記下來避免之後重蹈：

1. **Node 預設把 HTTP 標頭壓到第一次 `write()` 才送出。** 客戶端因此要等到第一個
   token 才收到回應標頭，量到的 TTFT 永遠是 0。SSE 伺服器必須明確 `flushHeaders()`。
   這件事對網關本身同樣成立——之後實作 `SseEmitter` 轉發時要確認標頭有立刻送出。
2. **客戶端斷線要監聽 `response` 的 `close` 並比對 `writableFinished`**，
   不能用 `IncomingMessage` 的 `close`（那在請求主體讀完時就會觸發）。
   這個缺陷還連帶讓統計失準：取消沒被偵測到，串流就繼續跑完並繼續累加 token 數——
   也就是「使用者早就離開，我們還在付錢」的實際樣貌。

第 2 點正好說明了為什麼 `cancelled` 統計端點是這個工具最重要的功能：
取消有沒有真的往上游傳，沒有這個數字就無從得知。

## 實作後補記（2026-08-26，路由與對沖骨架）

寫完 Provider 抽象與路由之後，用假 Provider 做端到端驗證，抓到四個缺陷。
四個都是「單看程式碼會覺得沒問題」的類型，且都只在**下游行為可控**時才驗證得出來——
這就是 `fake-provider` 排在第一優先的實際回報。

1. **主要 Provider 快速失敗時，備援根本不會被啟動。** 對沖與失敗切換共用了
   `max-attempts` 預算，導致 `max-attempts: 2` 的實際行為是「只試一家」。
   兩家健康的候選閒著，請求直接以 429 失敗。詳見 CLAUDE.md 的「對沖與失敗切換是兩件事」。
2. **對沖落敗者被記成故障。** 落敗者的串流被勝出者關閉，關閉引發的例外落進
   catch 區塊，於是呼叫了 `recordFailure()`。後果是慢一次就被降級，而降級之後
   更少被選中、更少被選中就更沒機會刷新統計——一次落敗變成永久降級。
   實際觀察到的現象是某一家 Provider 之後再也沒收到任何請求。
3. **失敗率用累計值、延遲用滾動窗口。** 兩者的時間尺度不一致，
   一小時前的故障會永遠留在分母裡。已改成與 TTFT 同樣的 128 筆窗口。
4. **冷啟動時的主要 Provider 是雜湊順序。** `ConcurrentHashMap#values()` 的迭代順序
   是任意的；統計全空時排序鍵全部相等，穩定排序保留的就是那個任意順序。
   設定檔裡刻意排第一位的主力 Provider 被無聲忽略。已改為保留註冊順序。

**方法論上的一點**：第 2 和第 4 點都是先看到「某家 Provider 的請求數是 0」才回頭找原因的，
不是讀程式碼讀出來的。斷言要落在**可觀測的數字**上（誰收到幾次請求、誰被取消幾次），
而不是「有沒有回 200」——回 200 的路徑底下可能藏著完全錯誤的行為。

另外踩到兩次同樣的坑：**前一個情境留下的統計會改變下一個情境的路由順序**，
導致斷言的前提（「fake-fast 是主要 Provider」）根本不成立，測出來的紅綠都沒有意義。
每個情境都必須在重啟後的乾淨統計上跑。

### `tools/verify-routing.js`

上述驗證已固化成腳本，共 8 個情境 14 項檢查，每個情境自動重啟網關以確保統計乾淨：

```bash
node tools/verify-routing.js
```

前置條件：`dev-stack` 已啟動（三個假 Provider）、`mvn install` 已產出 jar。

與 `stream-check` 的分工：這支管**誰被選中**（路由順序、對沖、失敗切換），
`stream-check` 管**串流過程本身**（緩衝、取消、token 完整性）。
兩者對「乾淨統計」的處理方式相反，見下一節。

## 實作後補記（2026-08-26，`stream-check`）

### 抓到的兩個缺陷

**1. 上游全掛時網關回 HTTP 200。** 三家假 Provider 全設成回 503，
網關回的卻是 `HTTP 200` 加一個錯誤事件。原因是 `SseEmitter` 一回傳給 Spring，
狀態碼就送出去了，之後才發現上游失敗。對只檢查狀態碼的客戶端、監控與重試中介層來說，
那是一次成功。已改成**先取得上游串流再建立 `SseEmitter`**，
在第一個 token 之前拋出的錯誤都還來得及變成正確的狀態碼。

**2. 標頭被壓到第一個 token 才送——這一項刻意沒有修。**
它與缺陷 1 的修法直接衝突（早送標頭就等於早承諾狀態碼），
也與「對沖以首個 token 決勝負」衝突。取捨與副作用記在 CLAUDE.md 技術決定 6。

值得記下的是：**兩個檢查同時變紅，才看得出它們其實是同一個取捨的兩端。**
只做其中一項檢查的話，很可能會朝錯誤的方向修。

### 兩支腳本對「乾淨統計」的處理相反

`verify-routing.js` 每個情境都**重啟網關**，因為它要斷言「誰被選中」，
而路由順序完全取決於統計。

`stream-check` 反過來，**把三家假 Provider 設成相同行為**，統計數字跨三家加總，
因此完全不依賴誰是主要 Provider，也就不需要重啟（快很多）。

選哪一種取決於斷言的內容。共通的教訓是：前一個情境留下的統計會改變下一個情境的前提，
不處理的話測出來的紅綠都沒有意義——這個坑在路由骨架階段踩過兩次。

### 沒紅過的斷言要證明自己不是空的

`stream-check` 的檢查 1 和 8 在開發過程中確實紅過，所以有效。
檢查 4（token 完整性）和 6（取消）從一開始就是綠的，因此另外做了靈敏度探測：
讓上游在第 10 個 token 後斷線（序號斷言變紅）、讓串流正常跑完不中斷（取消斷言變紅）。
三項都如預期變紅。

這個習慣值得延續到之後的 `cost-guard` 與 `rag-eval`：
**新增的檢查要先確認它能紅**，否則它只是讓報告變長，不會讓任何缺陷現形。

## 實作後補記（2026-08-26，`cost-guard` 與兩個 hook）

### 原始規劃裡有一項做不到

規劃寫的是「比對設定的每日上限是否真的會攔截」。實作時才發現**根本沒有每日上限可以比對**——
程式碼裡有三處註解假設它存在（`HedgePolicy` 說 immediate「必須有每日成本上限作為防線」、
`GatewayConfiguration` 啟動時警告「請確認已設定成本上限」），但沒有任何東西在執行它。

處理方式是讓 `cost-guard` 把「沒有攔截邏輯」本身列為一項警告，而不是靜靜地跳過那個檢查。
判準也因此訂成「有攔截邏輯（`throw`／`reject`／`deny`）」而非「有設定欄位」——
一個只有欄位沒有攔截的上限，比沒有上限更危險，因為它看起來像有防護。

### 抓到的另一個缺陷：測試替身造成的盲點

`parseUsage` 只從 `estimated_cost_cents` 取成本，而那是**假 Provider 才有**的欄位。
真 Provider 不回它時成本會記成 0——不會報錯，只是帳目上永遠看起來免費。

這是用測試替身開發特有的盲點：**替身比真貨多回了一個欄位，程式碼就理所當然地依賴它。**
替身該模擬的是真貨的限制，不只是它的能力。之後擴充 `fake-provider` 時要留意這個方向——
它目前還多回了 `provider` 欄位，同樣有被依賴的風險。

### 成本倍率是這支工具的核心數字

「一次客戶端請求會變成幾次上游請求」直接就是帳單的乘數。
它把對沖、失敗切換、重試全部收斂成一個可以持續追蹤的數字，
而且靈敏度很好驗：把對沖改成 `immediate`，它從 `1.00×` 精準跳到 `3.00×`。

### 兩個 hook 的嚴格程度刻意不同

| Hook | 時機 | 動作 |
| --- | --- | --- |
| `secret-guard` | `PreToolUse` | **阻擋寫入**（exit 2）|
| `cost-scan` | `PostToolUse` | 只提醒，且只在阻擋級發現時出聲 |

金鑰外洩沒有「其實沒關係」的情況，而且寫進 git 歷史後只能輪替金鑰，所以在寫入前擋。
成本風險常常需要人判斷（`immediate` 對沖有正當用途），機械式阻擋只會讓 hook 被關掉。

同理，`cost-scan` 不印警告級項目：那些是已知且記在文件裡的缺口，
每次存檔都刷一遍只會訓練大家忽略它。**被忽略的告警等於沒有告警。**

### 安全 hook 的誤報方向和漏報方向一樣重要

`secret-guard --self-test` 兩個方向都驗：七種真實金鑰格式要擋下來，
九種佔位寫法要放行——包括本專案文件裡的「金鑰樣式（`sk-`、`anthropic-` 等）」這一句。
它還會掃過整個專案，因為任何誤報都會讓這個 hook 在日常工作中被關掉，然後就什麼都不保護。

實作時踩到的一個具體問題：**hook 的測試樣本本身長得像真金鑰，會擋住對它自己的編輯。**
解法是同一行加 `secret-guard:allow` 註記。用「同一行」而不是「整檔排除」，
範圍最小，而且在 code review 時看得見——有人想用它偷渡真金鑰的話，那一行會很顯眼。
這個逃生口本身也列進了 self-test：沒驗過的例外機制，等到真的需要時才會發現壞掉。

### 一個 Node 的坑

`secret-guard.js` 同時是 hook 與被 `cost-guard` 引用的模組。
第一版沒有 `require.main === module` 判斷，於是 `cost-guard` 一 `require` 就觸發了 hook 主流程：
它讀 stdin、然後 `exit 0`，把引用它的腳本一起結束掉——**沒有任何錯誤訊息，只是整支腳本無聲地什麼都不做**。

## 實作後補記（2026-08-26，`bench`）

這一支的教訓幾乎全部關於**量測方法**，而不是被測系統。

### 我被自己的探測腳本騙了一次

寫 `bench` 之前先做了一支簡單的探測，得到「平台執行緒比虛擬執行緒快」這種違反直覺的結果，
接著又得到「暖機後 TTFT 73ms」——比上游設定的 150ms 還低，物理上不可能。

真相是：假 Provider 的容器在中途**整組消失**了，網關回的是錯誤，
而探測腳本只檢查「有沒有收到位元組」，於是把 25 條全部失敗的請求報成「成功 25，失敗 0」。

`bench` 因此要求每一條串流同時滿足三個條件才算成功：HTTP 200、確實收到 token、以 `[DONE]` 收尾。
**不驗證回應的壓測，數字越漂亮越危險**——失敗通常比成功快，所以會讓分位數變得更好看。

### 冷啟動的 JVM 差了近 7 倍

同樣負載下，冷啟動 TTFT `1188ms`、暖機後 `175ms`。沒暖機的對照組量到的是 JIT 而不是架構。
暖機用小批並行而不是完全序列——JIT 看的是請求次數，序列跑完一輪暖機要多花一分鐘。

### 有效性門檻用固定值，會獎勵表現差的那一組

第一版把「量測端 event loop 抖動 > 50ms」判為無效，結果**把表現最好的那一組判成無效**。

原因是抖動本身就是被測特性造成的：虛擬執行緒讓 100 條串流幾乎同時開始吐 token，
壓測端瞬間收到爆量；平台執行緒因為排隊，反而讓抵達變平順、抖動更低。

改成兩件事分開：
- **有效性**用比例（抖動 > 該輪 TTFT 的 25% 才算無效）——只擋掉「量到的主要是自己」的情況。
- **抖動即量測解析度**，小於它的差距一律不做宣稱。

這個改動立刻改變了結論的強度：`virtual` 相對基準線 +45ms，而解析度是 ±54ms，
所以正確的說法是「在這個負載下量不出網關的額外延遲」，而不是「網關只慢 45ms」。
同樣參數的另一次執行量到 +128ms（當時可宣稱）——網關開銷就落在解析度邊緣，
而平台執行緒的 +3150ms 任何一次執行都看得到。**兩個結論的強度不同，報告要能呈現這件事。**

### 刻意不報記憶體

第一版用 Windows 的 `WorkingSet64`，量到 11 MB——對 Spring Boot 應用顯然不可能。
Windows 會主動修剪閒置行程的 working set，而量測點正好在負載結束之後。
正確來源是 JVM 自己的指標（`/actuator/prometheus`）。在補上之前寧可不報：
**報告裡一個無法辯護的數字，比少一欄更糟。**

### 沿用自 FlowSentinel 的坑

Windows 上 `child.kill()` 殺不乾淨 JVM，殘留行程佔住連接埠，
下一組啟動失敗卻靜靜退出，於是負載全部打到上一組——**變成自己跟自己比**。
`bench` 用 `taskkill /T /F`，並在啟動後確認 `exitCode === null`、連接埠真的換人。

### 後續補上：記憶體改問 JVM

原本因為量不準而不報這一欄，後來改用 `/actuator/prometheus` 的
`jvm_memory_used_bytes{area="heap"}`——JVM 自己回報的數字，不受作業系統頁面調度影響，
每輪負載結束時取樣取最大值。**換成可辯護的來源之後才加回來**，
而不是為了讓報告看起來完整而留著一個錯的數字。

## 實作後補記（2026-08-26，`rag-eval`）

### 規劃的前提還不存在，但工具仍然做得出來

`rag-eval` 原本排在「接上向量庫後」。實作時專案**還沒有任何 RAG 程式碼**，
Qdrant 也是空的。做法不是延後，也不是做一支只會說「跳過」的空殼，而是讓它做三件現在就成立的事：

1. **定義並強制契約**——見下。
2. **量測 recall@k** 的機制備妥。
3. **用合成資料自我驗證**，證明這些檢查真的抓得到問題。

一般模式目前會如實報告「沒有東西可檢查」，不假裝通過。

### Qdrant 不記錄索引是誰建的，所以災難無從偵測

嵌入不一致是靜默失效，而 Qdrant **原生不記錄** collection 是用哪個嵌入模型建的。
不記的話，事後你只會看到「RAG 效果不好」——而那可以歸咎於一百種原因。

所以工具定義了契約：**每個 point 的 payload 要帶 `_embedding_model` 與 `_embedding_dim`**。
逐點記錄而不是整個 collection 記一次，是為了同時抓到**部分重建索引**
（一半舊模型、一半新模型），那種狀態比整個索引錯掉更難發現，
因為檢索結果會「有時候對、有時候不對」。

### 自我驗證把「靜默」量化了

固定裝置用詞袋嵌入（不是真模型，但「共用詞越多越相似」成立，所以 recall 有意義），
「換模型」以打亂詞→維度的映射模擬——**維度完全相同**，正是最危險的那種不一致：

| 情況 | recall@3 | Qdrant 回應 |
| --- | --- | --- |
| 同模型 | 100% | HTTP 200 |
| 不同模型（維度相同）| 46~54% | HTTP 200 |
| 隨機基線 | 30% | — |

兩次都是 HTTP 200。

### 門檻訂太緊會偶爾假紅

情境「不同模型 recall 應該崩掉」一度會間歇失敗：單次量測在 38%~50% 之間跳，
因為 Qdrant 的 HNSW 建圖有隨機性，且單一詞序排列可能剛好把某幾題排對。

改成對三個不匹配模型取平均（實測 46%~54%），門檻訂在同模型的 70%，留約 15 個百分點餘裕。
**訂在剛好貼著實測值會偶爾假紅，訂太鬆則抓不到真的退化**——
這跟 `bench` 的解析度問題是同一件事的兩種面貌：先知道正常的抖動有多大，才能訂門檻。

輸出也把隨機基線（3/10 = 30%）印出來。沒有基線的話，「46%」本身說明不了任何事。
