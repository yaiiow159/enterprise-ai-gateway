# 網關壓測

```bash
node .claude/skills/bench/bench.js
node .claude/skills/bench/bench.js --concurrency 200 --rounds 5
node .claude/skills/bench/bench.js --arms direct,virtual        # 跳過平台執行緒組
```

前置條件：`dev-stack` 已啟動、`mvn install` 已產出 jar。腳本會自行啟停網關。

## 與一般 QPS 壓測的差別

LLM 網關的每個請求都是**長連線、長時間、低 CPU**。「每秒完成幾個請求」不是重點——
使用者真正感受到的是**第一個字多久出現**，以及**同時能維持幾條串流而不劣化**。

所以這裡量的是 TTFT 分位數與並行串流下的穩定度，不是吞吐量。

## 三組對照

| 組別 | 是什麼 | 為什麼需要 |
| --- | --- | --- |
| `direct` | 壓測端 → 假 Provider，**不經過網關** | 基準線。沒有它就分不出「網關慢」與「假 Provider 慢」或「壓測端自己是瓶頸」 |
| `virtual` | 網關預設組態（虛擬執行緒） | 主要待測對象 |
| `platform` | 網關 + 平台執行緒，Tomcat 池上限 20 | 對照組 |

三組在**同一次執行、同一台機器**上取得，暖機條件相同。

平台執行緒組的池上限要明顯小於並行數，天花板才看得見。上游首字延遲也刻意設得長
（預設 800ms）：請求執行緒在 `ChatController` 裡會阻塞到第一個 token
（見 CLAUDE.md 技術決定 6），這段時間正是平台執行緒池被佔住的時間。
設太短的話兩組看起來一樣——不是因為沒有差別，而是因為差別還沒被逼出來。

## 每個設計都是被某次量錯逼出來的

**1. 每一條串流都要驗證**（HTTP 200、確實收到 token、以 `[DONE]` 收尾），三個條件缺一不可。

開發過程中假 Provider 曾經整組消失，而當時的探測腳本只看「有沒有收到位元組」，
於是把 25 條**全部失敗**的請求報成「成功 25，失敗 0」，我還從那些數字得出了錯誤的結論。
**不驗證回應的壓測，數字越漂亮越危險。**

**2. 暖機是必須的，而且各組要一致。**
冷啟動的 JVM 在同樣負載下 TTFT 是 `1188ms`，暖機後是 `175ms`——差了近 7 倍。
沒暖機的對照組量到的是 JIT，不是架構。

**3. 要有基準線。** 見上表。

**4. 量測端的抖動就是量測解析度。**
壓測端 event loop 塞住的話，量到的 TTFT 是自己的排隊延遲。腳本會量這個抖動，
並且**小於抖動的差距一律不做宣稱**。

門檻用「佔訊號的比例」而非絕對值，這一點是踩過才知道的：第一版用固定 50ms，
結果**把表現最好的那一組判成無效**。原因是抖動本身就是被測特性造成的——
虛擬執行緒讓 100 條串流幾乎同時開始吐 token，壓測端瞬間收到爆量；
平台執行緒因為排隊反而讓抵達變平順、抖動更低。固定門檻等於獎勵「上游被卡住」的那一組。

**5. Windows 上 `child.kill()` 殺不乾淨 JVM。**
殘留行程會佔住 8090，下一組啟動失敗卻靜靜退出，於是負載全部打到「上一組」——
**變成自己跟自己比，而兩組數字看起來都很正常**。所以用 `taskkill /T /F`，
並在啟動後確認行程還活著（`exitCode === null`）、連接埠真的換人了。

## 記憶體要問 JVM，不要問作業系統

第一版用 Windows 的 `WorkingSet64`，量到 11 MB——對一個 Spring Boot 應用顯然不可能，
而且兩組數字一模一樣。原因是 Windows 會主動修剪閒置行程的 working set，
而量測點正好在負載結束之後，拿到的是修剪後的殘值。

現在改用 `/actuator/prometheus` 的 `jvm_memory_used_bytes{area="heap"}`——
JVM 自己回報的數字，不受作業系統的頁面調度影響。每一輪負載結束時取樣、取最大值。
取不到就顯示 `—`，不猜。

一度考慮乾脆不報這一欄，因為**報告裡一個無法辯護的數字比少一欄更糟**。
換成可辯護的來源之後才加回來。

## 目前的結果（i9-12900H / 64GB / JDK 21.0.3）

並行 100 條串流、上游首字延遲 800ms、平台執行緒池上限 20。
最新一次的完整數字在 `docs/benchmark/`，包含逐輪原始值與重現指令。

**兩個結論的強度差很多，這件事比數字本身重要：**

| 結論 | 跨多次執行的觀察 | 強度 |
| --- | --- | --- |
| 平台執行緒明顯較差 | p95 一致落在 **4000ms 上下**，相對基準線 **+3150ms 左右**，tokens/s 只有虛擬執行緒的約 27% | 遠大於解析度，**任何一次執行都看得到** |
| 網關本身的額外延遲 | 相對基準線 **+45ms ~ +327ms**，而解析度是 **±50ms ~ ±144ms** | **落在解析度邊緣**，有時可宣稱、有時量不出來 |

所以正確的說法是「網關開銷小到不容易量出來」，而不是「網關只慢 45ms」——
後者把一次執行的結果當成常數，而實際上它隨機器負載在數倍範圍內變動。

平台執行緒的 p95 約 4000ms 與排隊模型相符：100 條並行 ÷ 20 條執行緒 = 5 批 × 800ms。

報告會逐輪列出原始數字與該輪的解析度，就是為了讓這個差別看得見。
**引用數字時要連同解析度一起引用**，否則就是把雜訊當成訊號。

## 報告

寫入 `docs/benchmark/<時間戳>.md`，包含執行環境（CPU／記憶體／JDK／OS）、
負載參數、每一輪的原始數字、有效性條件，以及可直接複製的重現指令。

沒有附上環境與參數的效能數字無法重現，也就沒有意義。
