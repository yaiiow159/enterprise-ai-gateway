# 成本風險把關

```bash
node .claude/skills/cost-guard/check.js            # 靜態 + 執行期
node .claude/skills/cost-guard/check.js --static   # 只做靜態（秒級，不需要環境）
node .claude/skills/cost-guard/check.js --runtime   # 只做執行期量測
node .claude/skills/cost-guard/check.js --requests-per-day 50000 --price-output 15
```

執行期量測需要 `dev-stack` 與網關都在跑；沒跑的話會自動略過並說明。

## 為什麼這個專案特別需要它

一般後端的 bug 是服務壞掉——會有人尖叫，會有告警。
**這裡的 bug 是帳單，而帳單要到月底才尖叫。**

無條件對沖、失控重試、沒有 `max_tokens` 的請求、忘了取消的串流，
任何一個都足以在無人注意的情況下持續燒錢，而系統看起來完全正常：
狀態碼 200、內容正確、延遲也沒變差。

## 靜態掃描（六項）

| # | 檢查 | 為什麼 |
| --- | --- | --- |
| 1 | 金鑰字面值 | 與 `secret-guard` hook 共用樣式。hook 擋「正在寫入的」，這裡掃「已經在檔案裡的」 |
| 2 | 請求一定帶 `max_tokens` | 沒上限的請求會生成到模型自己停下來 |
| 3 | 對沖是否為 `immediate` | 每個請求同時打 N 家，成本直接乘 N |
| 4 | 有沒有會**實際攔截**的每日成本上限 | 最後一道防線。判準是「有攔截邏輯」而非「有設定欄位」 |
| 5 | 成本歸戶會不會靜默記成 0 | 只讀上游回傳的成本欄位是陷阱，見下 |
| 6 | 重試有無退避與次數上限 | 無退避重試會把一次上游故障放大成自我 DDoS |

嚴重度分兩級：`阻擋` 讓腳本以非 0 結束，`警告` 只出現在報告裡。

## 執行期量測（四項）

**成本倍率**是這支腳本最重要的數字：一次客戶端請求會變成幾次上游請求。
它直接就是帳單的乘數——`1.0×` 表示沒有浪費，`3.0×` 表示帳單是三倍。
對沖、失敗切換、重試全都會推高它。

另外量測 `max_tokens` 有沒有真的傳到上游、客戶端斷線省下多少 token，
最後把 token 用量換算成每日成本。

**換算出來的金額是推估不是量測**：token 數是量到的，單價與日流量是假設，
所以報告會把假設值一起印出來。沒有附上假設的「每天會花 X 元」不可重現，也就沒有意義。

## 這支工具抓到並已修掉的兩個缺口

**1. 沒有任何每日成本上限的攔截邏輯。**（已修）
程式碼裡曾有三處註解假設它存在（`HedgePolicy` 說 immediate「必須有每日成本上限作為防線」、
`GatewayConfiguration` 啟動時警告「請確認已設定成本上限」），但沒有任何東西在執行它。

現在有 `BudgetLedger`：送出前預扣估算成本、實際成本出來後結算差額，
超限回 429 且**完全不打到上游**。支出與上限也輸出成 Prometheus 指標。

**2. 成本歸戶接上真 Provider 會靜默記成 0。**（已修）
`parseUsage` 曾經只從 `estimated_cost_cents` 取成本，而那是假 Provider 才有的欄位。
真 Provider 不回它時成本記成 0——不會報錯，只是帳目上永遠看起來免費。

這是典型的「用測試替身開發」會產生的盲點：替身比真貨**多**回了一個欄位，
於是程式碼理所當然地依賴它。替身該模擬的是真貨的限制，不只是它的能力——
所以 `fake-provider` 加了 `omitUsage` 設定，讓這條路徑測得到。

**兩者的修復有先後關係**：先修成本歸戶，再做上限。
反過來的話，上限會建在「每筆都記成 0」的帳上，變成一道永遠不會觸發的防線——
那比沒有更糟，因為它看起來像有保護。

## 兩個 hook，兩種嚴格程度

| Hook | 時機 | 動作 |
| --- | --- | --- |
| `secret-guard` | `PreToolUse` on Write/Edit | **阻擋寫入** |
| `cost-scan` | `PostToolUse` on Write/Edit of `.java`／`.yml` | 只提醒，不阻擋 |

差別是刻意的。金鑰外洩沒有「其實沒關係」的情況，而且一旦寫進 git 歷史就只能輪替金鑰，
所以要在寫入前擋下來。成本風險則常常需要人判斷——`immediate` 對沖有正當用途——
機械式地擋住寫入只會讓 hook 被關掉，然後它就什麼都不提醒了。

`cost-scan` 也**只在阻擋級發現時才出聲**。警告級的項目是已知且記在文件裡的缺口，
每次存檔都刷一遍只會訓練大家忽略它，而被忽略的告警等於沒有告警。

## 斷言要證明自己不是空的

沿用 `stream-check` 的習慣：新增的檢查要先確認它**能紅**。已驗證的：

| 刻意製造的情況 | 斷言反應 |
| --- | --- |
| 對沖改成 `immediate`（3 家） | 成本倍率 `1.00×` → `3.00×`，判為阻擋 |
| 設定檔改成 `policy: immediate` | 靜態掃描出聲，`cost-scan` hook 跟著出聲 |
| 不帶 `max_tokens` 直接打假 Provider | 產生 200 個 token（帶了則是 5），證明那條斷言在驗網關有沒有轉發 |
| `GATEWAY_BUDGET_ENABLED=false` | 「上限是否真的在記帳」判為阻擋，啟動日誌也大聲警告 |
| 上游設 `omitUsage`（模擬真 Provider）| 成本仍為非零（本地單價兜底），不是靜默的 0 |

`secret-guard` 自己也有 `--self-test`，同時驗漏報與誤報兩個方向：

```bash
node .claude/hooks/secret-guard.js --self-test
```

誤報方向特別重要——一個常常擋錯的安全 hook 會被關掉，然後它什麼都不保護。
本專案自己的文件就寫著「金鑰樣式（`sk-`、`anthropic-` 等）」，那必須放行。

## 逃生口

`secret-guard` 支援同一行加註記 `secret-guard:allow` 來跳過該行。
它自己的測試樣本就靠這個（樣本刻意長得像真金鑰，不排除的話 hook 會擋住對自己的編輯）。

用「同一行」而不是「整檔排除」：範圍最小，而且在 code review 時看得見——
有人想用它偷渡真金鑰的話，那一行會很顯眼。
