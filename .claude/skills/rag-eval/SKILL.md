# RAG 檢索品質把關

```bash
node .claude/skills/rag-eval/check.js              # 檢查現有 collection
node .claude/skills/rag-eval/check.js --self-test   # 用合成資料驗證檢查有效
```

前置條件：`dev-stack` 已啟動（Qdrant）。埠可用 `QDRANT_PORT` 覆寫。

## 要防的是什麼

嵌入不一致是**靜默失效**。用 A 模型建索引、用 B 模型查詢，向量庫照樣回傳最近鄰，
只是全部不相關。沒有例外、沒有錯誤碼、延遲也不變——系統不會壞掉，只會變笨。

維度不同會直接報錯（那算幸運）。**維度相同但模型不同才是災難**：
兩邊都「正常運作」，只有答案品質默默崩掉，而那可以歸咎於一百種原因。

自我驗證跑出來的實際數字：

| 情況 | recall@3 | Qdrant 回應 |
| --- | --- | --- |
| 索引與查詢同模型 | **100%** | HTTP 200 |
| 索引與查詢不同模型（維度相同）| **46~54%** | HTTP 200 |
| 隨機亂猜的期望值 | 30% | — |

兩次都是 HTTP 200。這就是「靜默失效」的樣子。

## 這個工具定義的契約

Qdrant **原生不記錄** collection 是用哪個嵌入模型建的。不記的話，上面那個災難
事後根本無從偵測。所以本工具要求：

> 每一個 point 的 payload 都要帶 `_embedding_model` 與 `_embedding_dim`。

**逐點記錄而不是整個 collection 記一次**，是為了同時抓到**部分重建索引**——
一半的點來自舊模型、一半來自新模型。這種狀態比整個索引錯掉更難發現，
因為檢索結果會「有時候對、有時候不對」。

專案設定端則要在 `application.yml` 宣告 `gateway.rag.embedding-model` 與
`embedding-dimension`，工具才有比對基準。

## 檢查項目

| 檢查 | 抓的是什麼 |
| --- | --- |
| point 有宣告嵌入模型 | 沒宣告 = 事後無從偵測不一致 |
| collection 內模型一致 | 部分重建索引 |
| 索引模型 = 設定模型 | 最危險的那種靜默失效 |
| 維度與距離度量相符 | 維度不符會報錯，算幸運 |
| collection 非空 | 空索引檢索結果一律為空，但不報錯 |
| recall@k | 換模型或改分塊策略時的迴歸基準 |

## 目前狀態：還沒有東西可檢查

**本專案還沒有 RAG 程式碼，Qdrant 也還沒有任何 collection。**
所以一般模式目前會如實報告「沒有東西可檢查」，而不是假裝通過。

`--self-test` 用合成資料證明這些檢查真的抓得到問題，所以等真的 RAG 進來時，
工具已經備妥且驗證過，契約也已經寫在這裡讓實作照著做。

## 自我驗證怎麼做的

固定裝置用的是**詞袋嵌入**，不是真的模型——但它有真實模型的關鍵性質：
共用詞越多越相似，所以 recall@k 是有意義的數字而不是隨機值。

「換模型」以打亂「詞→維度」的映射來模擬：**維度完全相同**，只是空間不同。
這正是最危險的那種不一致。

五個情境：

1. 同模型索引與查詢 → recall@3 應該高
2. 不同模型（維度相同）→ recall@3 應該崩到接近隨機，且 **Qdrant 不報錯**
3. collection 混雜多個模型 → 應該被抓到
4. point 缺少模型宣告 → 應該被抓到
5. 維度不符 → Qdrant 應該明確報錯（HTTP 400）

### 門檻怎麼訂的

情境 2 的判定一度會偶爾假紅：單次量測在 38%~50% 之間跳，
因為 Qdrant 的 HNSW 建圖有隨機性，而且單一詞序排列可能剛好把某幾題排對。

改成對三個不匹配的模型取平均（實測 46%~54%），門檻訂在同模型的 70%，
留約 15 個百分點的餘裕。**訂在剛好貼著實測值會偶爾假紅，訂太鬆則抓不到真的退化。**

輸出也把隨機基線（3/10 = 30%）一起印出來，讓 recall 數字可以被解讀——
沒有基線的話，「46%」本身說明不了任何事。
