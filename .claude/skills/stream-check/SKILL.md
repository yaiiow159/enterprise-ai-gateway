# SSE 串流轉發驗證

```bash
node .claude/skills/stream-check/check.js
node .claude/skills/stream-check/check.js --verbose
```

前置條件：`dev-stack` 已啟動，且網關正在 8090 埠執行。
埠可用 `GATEWAY_PORT`／`FAKE_FAST_PORT`／`FAKE_SLOW_PORT`／`FAKE_FLAKY_PORT` 覆寫。

## 為什麼需要專門的工具

串流的錯法幾乎都是「看起來正常」的。內容最後都會出現、狀態碼是 200、
瀏覽器裡手動點一次也看不出問題——差別只在使用者要多等幾秒，或是我們多付了幾秒的錢。

一般的 HTTP 測試工具只看最終結果，而串流的錯誤全部藏在**過程**裡：
什麼時候到、分幾次到、中斷的時候怎麼表達。這些都要在時間軸上量才看得見。

## 八個情境，十九項檢查

| # | 情境 | 抓的是什麼錯 |
| --- | --- | --- |
| 1 | 標頭不應等到整段生成完 | 中間有人把整個串流緩衝起來 |
| 2 | TTFT 應反映上游首字延遲 | 同上，但從內容抵達的角度量 |
| 3 | chunk 應逐段抵達 | 收完整段才一次轉發 |
| 4 | token 不遺漏、不重複、順序正確 | SSE 事件邊界處理錯誤 |
| 5 | 正常結束應有明確收尾 | 少了 `[DONE]` 或 `finish_reason` |
| 6 | 客戶端斷線後上游應被取消 | **使用者離開後還在付錢** |
| 7 | 中途斷線要能與正常結束區分 | 半截答案被當成完整答案 |
| 8 | 尚未送出內容就失敗要反映在狀態碼 | 失敗被當成成功 |

## 設計上的一個選擇：不假設誰是主要 Provider

每個情境都把三家假 Provider 設成**相同行為**，需要統計數字時跨三家加總。

原因是路由順序會被前一次請求的延遲樣本與失敗紀錄改變。若斷言的前提是
「fake-fast 會服務這次請求」，那前提隨時可能不成立——實際踩過兩次，
兩次都是測出來的紅綠完全沒有意義，而且第一時間看不出來。

代價是這支腳本驗不了「誰被選中」，那是 `tools/verify-routing.js` 的職責。

## 開發時抓到的兩個缺陷

**1. 上游全掛時網關回 HTTP 200。**
`SseEmitter` 一回傳給 Spring，狀態碼就送出去了，之後才發現上游失敗，
就只能補一個錯誤事件。對只檢查狀態碼的客戶端、監控與重試中介層來說，
那是一次成功——上游三家全掛也一樣。

修法是**先取得上游串流再建立 `SseEmitter`**：`HedgingChatClient#stream` 會阻塞到
某個候選送出第一個 token，在那之前拋出的錯誤都還來得及變成正確的狀態碼。

**2. 標頭被壓到第一個 token 才送。**
這一項最後**沒有修**，因為它與更重要的性質衝突：標頭一送出狀態碼就定案，
正是缺陷 1 的成因；而對沖依定義要以首個 token 決勝負（CLAUDE.md 技術決定 4），
在第一個 token 之前網關根本還不知道會由誰服務、甚至不知道有沒有人能服務。

誠實的狀態碼比提早幾百毫秒的標頭重要，所以標頭與第一個 token 綁在一起送。
檢查 1 因此改成守住**剩下那個真正的錯法**：標頭被拖到整段生成完才送。

要留意的副作用：TTFT 很長時，中間的反向代理可能因為遲遲沒有位元組而先逾時。
真的遇到再考慮送 SSE 註解行（`: ping`）保活，但那等於提前承諾狀態碼，要一起評估。

## 斷言要證明自己不是空的

檢查 1 和 8 在開發過程中確實紅過，所以它們有效。
檢查 4 和 6 從一開始就是綠的——沒紅過的斷言可能根本沒在測東西，
所以另外做了靈敏度探測：讓上游在第 10 個 token 後斷線（序號斷言變紅）、
讓串流正常跑完不中斷（取消斷言變紅）。三項都如預期變紅，斷言是活的。

改動這支腳本時請維持這個習慣：**新增的檢查要先確認它能紅**，
否則它只是讓報告變長，不會讓任何缺陷現形。

| --- | --- |

| `tools/verify-routing.js` | 路由順序、對沖、失敗切換 |
